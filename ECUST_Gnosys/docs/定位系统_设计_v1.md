# 定位系统设计 v1

> 状态：设计稿，待审查。本项是 L1/L2/L3/L4 的**地基**，先于章节层实现。
> 触发原因：实测发现"EPUB 标题导不进来"、"前端 60 行章标题模糊匹配"、"L2 只能按 chapter_id 存"三个症状**是同一个根因**——章/段落坐标有三套，且段落没有稳定身份。

---

## 1. 为什么要先做它

四个层级的所有产出**都存在坐标上**：L2 的区块锚点、L3 的段落笔记、L4 的义项范围（"第一至二章"）、前端的正文高亮回溯。坐标不稳，每次重新切分/重新入库都让上层数据失效。

现状（实测）：

```
章坐标    spine_order（入库块） ／ chapter_id（DB 行） ／ chapter_idx（阅读器逻辑章，各层实际在用）
标题来源  chapters.heading_json（epub 的 h1-h6）／ heading_level 正则（文本推断）／ build_heading_based_toc（阅读器自己在统一 HTML 上再检测一遍）
段落身份  (chapter_idx, paragraph_index)：每次调用现解 HTML 得到，不落库
```

三类症状：

| 症状 | 实测 |
|---|---|
| EPUB 标题丢 | `book_outline.headings_from_field` 只读逻辑章对应的**那一个** spine 行的 `heading_json`；而阅读器常把多块拼成一章 → ci=2 导言（164 段）只拿到 1 个标题、ci=4 第一章（172 段）只 1 个；ci=5 拿到 5 个 |
| 前端绕路 | `reader.html` 有 ~60 行"章标题前缀模糊匹配"（因为 L2 按 `chapter_id` 存，与阅读器索引不一致） |
| 表自相矛盾 | `chapter_units` 事后把段落搬给阅读器的章，却不动 `content_text` → 17/28 章两个数差十几倍（spine=5：153 段/28,403 字 vs `content_text` 24 字）；**而全应用没人读这两张表** |

**目标：一条主坐标 + 一份结构事实，其余都是它的派生物。**

## 2. 主坐标

```
Locator = (book_id, chapter_idx, paragraph_index, fingerprint)   # 加书=全局唯一
```

- `chapter_idx`：阅读器逻辑章索引，**唯一对外的章坐标**。
- `paragraph_index`：该书该章内的段序（0 起）。
- `fingerprint`：段落规范化文本的哈希 —— **不是主键，是校验位**。重切/重入库时用它检测偏移（报警，不自动迁移）。
- `spine_order` / `chapter_id` 降为**内部实现细节**，不再对外暴露，也不再用作任何存储键。

稳定性由"段落落库"保证：解析规则与 HTML 不变 → 位置不变；变了 → 指纹报警。

## 3. 数据契约

### 3.1 新表 `book_paragraphs`（唯一段落真相）

```sql
CREATE TABLE IF NOT EXISTS book_paragraphs (
    book_id      INTEGER NOT NULL,   -- = books.id（整数外键）；API 参数 book_id 是文件夹名，内部先解析
    chapter_idx  INTEGER NOT NULL,
    para_index   INTEGER NOT NULL,
    fingerprint  TEXT    NOT NULL,
    text         TEXT    NOT NULL,
    section_path TEXT,              -- JSON 数组，如 ["一、事物的简单概念"]；NULL/[] = 不在任何节下
    char_count   INTEGER NOT NULL,
    built_at     TEXT    NOT NULL,
    PRIMARY KEY (book_id, chapter_idx, para_index)
);
CREATE INDEX IF NOT EXISTS idx_bp_fp ON book_paragraphs(book_id, fingerprint);
```

它同时提供三件事：**内容**（text）、**位置**（chapter_idx + para_index）、**结构归属**（section_path）。四层要的取数全从这里出。

### 3.2 标题树 = `book_paragraphs` 的派生物（不再单独存）

- 节点 = 连续相同 `section_path` 的段落聚合；节点区间 = 首末 `para_index`。
- 层级：epub 源用 `chapters.heading_json`（**按逻辑章聚合它覆盖的全部 spine 块**），否则用文本模式推断（`heading_level`）。判定一次，写进 `section_path`。
- **标题匹配要归一化**：`heading_json` 的文本可能带 `\r\n`、首尾空白、全半角差异（实测有 `'\r\n 第二节　黑格尔对科学体系的理解'`），所以比对前先过 `normalize_text`；仍对不上的标题**不编位置**（保持现状），但计入构建报告。
- 好处：**一个来源**。L1（章列表）、L2（章节层级树）、L3（所属节/窗口）、L4（scope 章区间）看到的是同一棵树。

### 3.3 现有表的处置

| 对象 | 处置 | 理由 |
|---|---|---|
| `paragraphs` 表 | **废掉**（连同 `chapter_units.py`、`tools/platform/check_chapter_units.py`） | 全应用无人读；被补丁改成自相矛盾，留着只会继续误导 |
| `chapters.para_count` | **弃用** | 章行是 spine 行的，装不了逻辑章的段数（正是它变成 153 vs 24 的原因）。逻辑章段数从 `book_paragraphs` COUNT 取 |
| `chapters.content_text` | 不动 | 服务端已在代码注释里声明不使用 |
| `books.toc_json` | **修好写库** | 现在恒为 `'[]'`（INSERT 传 `'[]'` 后无 UPDATE）；全仓无人读，但目录是产品该有的数据 |

## 4. 接口（对外签名不变）

| 接口 | 变化 |
|---|---|
| `agent_book.logical_paragraphs(book_id, chapter_idx)` | 内部改为**查表**；表不存在时回退现解（未重建的书不炸）。返回结构不变：`(chapter, paragraphs, total)`，段落仍带 `paragraph_index`/`text`/`fingerprint`，**新增 `section_path`** |
| `agent_book.locate(book_id, chapter_idx, para_index)` | 新增：单段 + 所属节路径 |
| `agent_book.find_by_fingerprint(book_id, fingerprint)` | 新增：内容反查位置（供上层校验） |
| `book_outline.structure(book_id, chapter_idx)` | 改为由 `section_path` 派生（同一份数据），噪声规则修正 |
| `book_outline.section_context(...)` | 不变（窗口仍 6000 字上限） |
| 四个工具 | **零改动**（`read_text`/`search_text`/`read_outline`/`read_notes` 的签名与行为都不变） |

## 5. 重建脚本（机械）

`tools/platform/build_book_paragraphs.py`

```
1. 遍历逻辑章（_build_chapters）
2. 每章取切片 → 按现有同一套切段规则切段 → 写 book_paragraphs（含 fingerprint）
3. 结构：取该逻辑章的字节区间（_chapter_slice_anchors 已支持 __byte__ 回退），
   聚合区间内**全部** spine 块的 heading_json（修 1:1 假设）；缺则文本模式推断；
   标题按文本逐字匹配到段落 → 写 section_path
4. 重复运行时比对指纹：报告"位置变了 / 新段 / 消失段"（只报警）
5. --check 只报告不写；--book 限定单本
```

只写 `book_paragraphs`，**不动 `content_html`**（避免书库二进制产生巨大 diff）。

## 6. EPUB 导入修三处

1. **`books.toc_json` 写回**：把 `parse_toc_recursive`（或兜底 `get_fallback_toc`）的结果写进库。
2. **章标题匹配归一化**：现在是 `t.file_href == item.get_name()` 严格相等 → 7/28 章沦为 `Section N`。改为：双方都去 `#锚点`、取 basename、`normalize_text` 后比对（兼容 href 带 `OEBPS/text/` 前缀、扩展名大小写差异）。
3. **删掉 `chapter_units.align_paragraphs` 调用**：段落归属改由 `build_book_paragraphs` 直接按阅读器的章切分（不再事后搬）。

## 7. 前端

删掉 `chapterLayerIdxFor()` 的标题模糊匹配（~60 行）与 `_chLayerList` 缓存，章节层面板直接用 `currentChapter`。L2 的存储键在章节层规格里同步改为 `chapter_idx`。

| 2 | 重复重建：指纹全等（幂等） |

现有 19 个单测须全过。已有 L3 记录（1425 条，键为文本哈希）与 L4 数据（键为词）**不受重建影响**。

## 9. 风险

1. `logical_paragraphs` 是四层都在用的函数 —— 对外签名不变，只换内部实现；改动前后跑第 8 节第 1 条对比。
2. **与另一会话的冲突**：`agent_book.py`、`book_service.py`、`schema.py`、`reader3.py` 都是共享文件，动手前先确认那个会话没在改。
3. 书库 db 是 git 跟踪的二进制：本项只写新表，避免巨大 diff；**不重跑入库**（除非要修 toc_json 与标题回填，那需要 --force 单本重跑）。
4. `chapter_units` 删除后，`paragraphs` 表的历史数据没有消费者，可安全 `DROP TABLE`（在重建脚本里加 `DROP TABLE IF EXISTS paragraphs`）。

## 10. 本项不做

- 不做段落自动迁移（指纹只报警）。
- 不做江村经济的切分修复（另立项；它修好后跑同一个 `build_book_paragraphs` 即可）。
- 不新增工具、不改工具签名、不改判定标准。
