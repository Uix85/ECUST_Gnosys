# 概念层（L4）需求概念化 v1

记录日期：L4 需求首次梳理。本文只做概念化，不写实现。

## 0. 一句话

用户在阅读器里**划词**，AI 针对「这个词 + 这一句的语境」给出解释，并说明它在全书中的定位与演化。

## 1. 交互形态（需求 1、2）

- **触发**：解释笔 + 划词，**按需单次**，不是批量预生成。
  （现有前端：`#bb-concept` 开关 → 选中文本 → `auxClassify()` 恒返回 `concept` → 建 `<mark class="concept-hl">` → `GET /api/layer/concept/{book}?term=…`）
- **前置**：L1 全书层、L2 章节层、L3 语义层**已提前生成**，作为概念层的语境材料。
- **响应路径必须带缓存**：词条已存在 → 直接显示；不存在 → 才触发一次 agent 运行。
  这与 L3（后台批量跑、可以慢慢来）是两种完全不同的运行形态。

## 2. 三条铁律（需求 3）

1. 解释**不得**用词典义或一般学术定义替代。
2. 解释必须锚定**当下位置**（章 / 段 / 句）。
3. 词义随文本演化 → **同一字形在不同位置可以给出不同解释**。
   例：《精神现象学》的「对象」在导言、感性确定性、知觉章、自我意识章不是一回事。

## 3. 适用范围：本层的核心概念（需求 6 + 组长设想）

用「适用范围」把「这个词的意思管多宽」形式化，四个取值：

| scope | 含义 | 是否必须在解释里声明 |
|---|---|---|
| `book` | 全书一致，无变化 | **不声明**（默认沉默） |
| `chapter` | 仅本章成立 | 必须声明 |
| `sentence` | 仅当前这一句/这一段成立 | 必须声明 |
| `shifting` | 随文本演化，有多个义项 | 必须声明，且要给出义项序列与转折位置 |

**默认沉默规则**：全局一致的情况不专门说明；只有 `chapter` / `sentence` / `shifting` 才必须显式交代。
这与需求 6 的原话一致：「全局一致的情况一般就不需要说明，只有特别的需要说明。」

输出中另需单独回答两个问题（需求 6）：

- 这个词在书中**是否有明确的定义**（有则指出定义出现的位置；没有则明说"书中未给出定义"）。
- 该定义**是否全局生效**（= 上面那个 scope）。

## 4. 一致性要求（需求 4）

- **同义互指**：全书意思相同的概念，应能相互对应（指向同一义项）。
- **演化呼应**：概念存在历史变化时，应交代它从哪个义项走到哪个义项、在何处转折。
- 机制上：一致性不是「生成时顺手回忆一下」，而是要**靠工具真的去查全书出现位置**再下判断。

## 5. 概念化后的数据模型（三级）

```
term（字形，如「对象」）
  └── sense（义项，含义单元，一个 term 可有多个）
        └── occurrence（实例，某章某段某句的一次出现）
```

现有表的情况：

| 表 | 现状 | 与需求的差距 |
|---|---|---|
| `concept_layer` | `UNIQUE(book_id, term)`，键＝词条名 | **只能装一级**，一个词全书只能有一条解释 |
| `concept_occurrences` | 只有 `concept_id + paragraph_id`，**从未使用** | 正好可以承担 occurrence 一级，但需要补 `sense` 归属 |

**这是本次需求最大的结构性冲突**：`GET /api/layer/concept?term=…` 是按 term 查唯一一条，
而需求 3 要求同一词在不同位置含义不同。两条路：

- **A. term 唯一 + content 内分义项**：改动最小，弹窗按当前语境选义项显示。
- **B. (term, 位置) 多行**：直接对应需求，但要改唯一键与查询接口。
- **C（倾向）**：term 级存「全局谱系」（有无明确定义、是否全局生效、义项时间线），
  occurrence 级存「当下这句怎么读」。需求 6 天然落在 term 级，需求 3 天然落在 occurrence 级。

## 6. 与其它层的关系（需求 6 后半）

主要配合 **L3 语义层**：L3 的段落笔记就是"这个词在此处的语境"最直接的材料，
`read_existing_note` 已经能同时返回 `semantic` 层内容与该段涉及的 `concepts`。
L1/L2 提供的是"这个词在全书/本章的位置感"。

## 7. Skill（规程）该管什么、Tools 该管什么

**分工结论：Skill 管判定顺序与默认沉默规则；Tools 管取证。**

Skill 规程草稿（判断顺序）：

1. 先定位：当前划的词在**哪一句、哪一段、哪一章**（材料里带位置，不要自行脑补）。
2. 取证：查该词在**全书**的所有出现（至少：首现、当前位置、之后的关键处）。一律以文本为准。
3. 判定 `scope`（第 3 节的表）。
4. 若当前位置的读法与已有义项冲突 → **明说演化或区分**，不得硬合并成一条。
5. 输出：有无明确定义 / 当下读法 / 适用范围 / 与别处的呼应。
6. 引文必须核验（沿用 `book-reading` 的既有规则：只用本任务已读原文）。

Tools：

- **复用**：`get_book_outline`、`search_book_text`、`read_book_paragraph`、`read_existing_note`、`verify_source_quote`
- **新增候选**：`find_term_occurrences`（同一词全书定位，按章排序，用来支撑 scope 判定与一致性）
- **新增候选**：`read_concept_entry`（读该词已有词条/义项，用来避免自相矛盾）
- **任务工具（终止）**：`submit_concept`

## 8. 输出 schema 草案

| 字段 | 含义 | 校验 |
|---|---|---|
| `has_definition` | 书中是否有明确定义 | 为真时必须给出位置 |
| `definition_note` | 定义内容或"书中未定义" | 非空 |
| `reading` | 当下语境的读法 | 非空、必须结合本句 |
| `scope` | `book` / `chapter` / `sentence` / `shifting` | 枚举 |
| `scope_note` | 适用范围说明 | **scope ≠ book 时必填**（默认沉默规则的落地） |
| `links[]` | 同义互指或演化呼应的位置 | 目标位置必须真实存在 |
| `quotes[]` | 引文 | 必须能在材料账本中逐字核到 |

## 9. 待拍板（需要确认后才能写实现）

1. **多义怎么落库**：走第 5 节的 A / B / C 哪条？（影响表结构与接口）
2. **划词是同步等待吗**：用户在界面上等结果 → 预算只能给很少几次模型请求，不能跑长循环。
3. **要不要人工核稿**：直接显示，还是像 L3 一样先落"待核稿"。
4. **一致性谁来做**：生成时顺带判断，还是另设一个"全书画一"的巡检任务事后收敛。
5. **词条边界**：用户划的可能是词组或短句（现有 `auxClassify` 不限制长度），要不要限制为词/术语？
6. **占位逻辑要撤掉**：`save_concept` 现在"content 缺省时填全书层文本"是占位，接入 AI 后必须删除，否则会污染数据。

# 附录：需求缺口与补充建议（v1.1）

以下每条都是「现在需求没说、但不定义就没法写实现」的点。

## A. 判定标准类（决定 validator 能不能写）

1. **「算不算一个新义项」没有判定标准。**
   什么时候是「另一个义项」，什么时候只是「同一个义项的变体」？必须给判据（建议：两处解释**互相矛盾或外延不能相容**才算新义项），
   否则模型会随便切义项、或把明显的变化硬合成一条 —— 两种都直接破坏需求 4 的一致性。
2. **合格线缺失。** L3 有三条硬校验（字段齐 / 逐句数对齐 / 引文逐字在账本里），L4 目前一条也没有。
   建议最小集：引文必须逐字核验 · `has_definition=true` 必须给出原文位置 · `scope≠book` 必须有说明 · `shifting` 必须给出至少两个位置且引文可核。
   没有这一组，「终止标准」就无从落地。
3. **日常义 vs 文本义的辨析是必出项，但现在需求里没有。**
   申报书把这条写成本层最有价值的产出（「日常'个性化'理解为体现个人品味，鲍德里亚揭示它是系列预设的边缘性差异」）。
   建议强制 `common_reading` 字段（日常/字面读法），与 `reading` 并列展示 —— 这也正好是可校验的。

## B. 边界与成本类

4. **划词边界没定义。** 用户可能划「对象」，也可能划「这个对象本身」甚至半句话。
   建议：term 长度上限 + 停用词拒绝 + 划到句子时把它当**语境**而不是 term，否则 `concept_layer` 会被垃圾词条污染。
5. **缓存与语境冲突（最关键）。** 现在缓存键是 `term`，同一个词在第二章和第五章划会命中同一条，**直接违背需求 3**。
   必须定：缓存 term 级「词条+义项表」，显示时按当前位置选义项；或者缓存键包含语境指纹。
6. **缺少渐进式输出。** 用户在界面上等着，不能回一段长文。
   建议分两级：**先给一句人话读法（必须快、必出）**，再给「全书定位 / 是否演化 / 定义是否全局」的详情（可慢、可展开）。
7. **L3 没跑到的段落怎么办。** 概念层要配合 L3，但 L3 可能还没生成过该段。
   建议明确：**不现场生成 L3**，降级为只用原文 + L1/L2。不写进需求就会出现「依赖一个不存在的语义层」。

## C. 一致性与稳定性类

8. **译名卡一致性必须继承。** L3 的规范里已有一条硬规则：卡内术语的解释必须与译名卡一致。
   需求 4 只说了层内一致（同义互指、演化呼应），漏了**层间一致**。L4 必须继承，否则同一个词在两层解释打架。
9. **义项 id 必须稳定。** 重跑一次概念层，义项编号不能变，否则 L3 的引用、前端高亮、用户书签全会断。
   建议：义项按**首次出现位置**排序，id 取位置指纹，而不是按生成顺序临时编号。
10. **一致性的收敛时机。** 生成时只能看见已存在的义项；新义项出现后，旧义项要不要回头补「演化呼应」？
    建议 v1 **不做回写**，改为提供一个离线巡检脚本（与 `scripts/check_*` 同一形态），否则每生成一个词条都要重跑全书。

## D. 验证类

11. **需要黄金用例。** 至少准备 3～5 个已知多义词（对象 / 精神 / 意识 / 自在自为 / 扬弃），
    每次改 prompt 或工具后人工看一遍输出。这是唯一能防住「看起来像那么回事」的手段。
